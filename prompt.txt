4. Data Acquisition Layer — Open-Source Only

4.1 Abstract interface

Define one AcquisitionAdapter ABC with these methods:

```python
async def fetch_tweet(tweet_id: str) -> Optional[dict]
async def fetch_replies(tweet_id: str, limit: int = -1) -> list[NormalizedReply]
async def fetch_poll(tweet_id: str) -> Optional[NormalizedPoll]
async def fetch_likers(tweet_id: str, limit: int = -1) -> list[dict]
async def fetch_reposters(tweet_id: str, limit: int = -1) -> list[dict]
def capabilities() -> dict  # {"poll": bool, "replies": bool, "individual_likers": bool, "individual_reposters": bool, "auth_required": bool}
```

Normalized models must include source_tool, auth_tier ("none" | "guest" | "auth_token" | "session"), and all fields listed in Section 8.

4.2 Concrete adapters to implement

XTweetFetcherAdapter (auth_tier: "none")

· Wrap the open-source x-tweet-fetcher CLI/library.
· Use FxTwitter for single tweets; use a self-hosted Nitter instance (http://127.0.0.1:8788) for replies, timelines, and search.
· Capabilities: poll=False, replies=True, individual_likers=False, individual_reposters=False.
· Do not rely on public Nitter instances—require the operator to configure their own.

TwscrapeAdapter (auth_tier: "auth_token")

· Wrap the twscrape Python library with an AccountsPool.
· fetch_poll: read tweet_details().card.options (each with label, votesCount) and card.finished; compute total_votes = sum(votesCount).
· fetch_replies: stream api.tweet_replies().
· fetch_likers: api.favoriters(). fetch_reposters: api.retweeters().
· Capabilities: all True.
· Rely on twscrape's built-in account rotation for rate limits; still enforce the orchestrator's global concurrency cap.

XCliAdapter (auth_tier: "session")

· Wrap the Go binary x (strictly read-only).
· Run commands with -o jsonl and parse line-by-line JSON.
· fetch_poll: x poll <id> → map options[].label and options[].votes.
· fetch_replies: x replies <id> -n <limit>.
· fetch_likers: x likers <id>. fetch_reposters: x retweeters <id>.
· Session cookie imported into the session directory only; never logged or exported.

ScweetAdapter (auth_tier: "auth_token")

· Wrap the Scweet Python library.
· fetch_replies and fetch_reposters implemented. fetch_poll returns None (Scweet does not document a poll method).
· Purpose: redundant Tier 2 coverage when twscrape accounts are throttled.
· Capabilities: poll=False, replies=True, individual_likers=False, individual_reposters=True.

4.3 Router

Implement AcquisitionRouter as the single entry point for the rest of the application. It:

1. Sorts adapters by operator-configured tier preference (default: x-tweet-fetcher → x-cli → twscrape → Scweet).
2. Skips adapters whose capabilities() do not include the requested method.
3. Skips adapters requiring credentials that are not configured.
4. Returns the first non-empty, non-None successful result.
5. On RateLimitError or CollectionError, logs the adapter failure, records it in CollectionStatus, and falls through to the next adapter.
6. Raises CollectionError listing all adapter failures if no adapter succeeds.
7. Sets collection_status = "partially_complete" when a lower-capability adapter supplied the data while a higher one was unavailable.

The router must never fabricate data. Missing polls, missing likers, or failed reply fetches must be surfaced as explicit limitations.

4.4 Configuration file

Ship a documented config/acquisition.yaml with this shape and no real credentials:

```yaml
acquisition:
  preference_order: [x-tweet-fetcher, x-cli, twscrape, Scweet]
  x_tweet_fetcher:
    enabled: true
    nitter_base: "http://127.0.0.1:8788"
  x_cli:
    enabled: true
    binary: "x"
    session_cookie_env: "XCLI_SESSION_COOKIE"
  twscrape:
    enabled: true
    accounts_db: "${SESSION_DIR}/twscrape_accounts.db"
    account_source_env: "TWSCRAPE_ACCOUNTS"
  scweet:
    enabled: false
    auth_token_env: "SCWEET_AUTH_TOKEN"
```

All credentials load from environment variables. If a credential is absent, the adapter is disabled silently (not a startup crash). Never write credentials into competition config exports, logs, screenshots, agent prompts, or JSON.

5. Voting Method Registry

Each voting method is an independent adapter that feeds the same normalized event pipeline:

· Native X poll — collect aggregate counts via twscrape or x-cli. Preserve option labels verbatim. Do not create synthetic individual vote records. Display: "Individual voter verification unavailable for anonymous aggregate poll votes." Do not reconstruct exact counts from rounded percentages unless the operator explicitly enables estimation and the result is labeled as an estimate.
· Reply/comment — configurable aliases, hashtags, keywords, word boundaries, multi-language aliases. Do not assume any reply containing a project name is a vote.
· Like-based — distinguish aggregate like counts (FxTwitter/Nitter) from individually observed liker identities (twscrape/x-cli). Never infer who liked from unrelated activity.
· Repost-based — capture account ID and event timestamp where exposed. Distinguish reposts from quote posts when rules require it.
· Quote-post — configurable phrase, mention, hashtag, or support-statement rules. Quote-posting the source post alone never automatically qualifies.
· Mention-based — allow association via configured accounts; classify as vote, neutral mention, criticism, question, spam, or ambiguous.
· Hashtag/keyword — required/excluded patterns, word boundaries, language-specific aliases, conflict precedence.
· Combined/weighted — the operator must choose whether the leaderboard uses separate counts, combined raw count, unique account-method pairs, weighted score, or a custom formula. Document every formula. Never silently sum incompatible measures; never merge poll aggregates with individual records.
· External/manual — CSV, JSON, spreadsheet exports, manual totals, screenshot/OCR with operator-supplied confidence labels. Every external source has its own provenance and confidence classification.

Design the registry so new adapters can be added without rewriting the application. Do not execute arbitrary code uploaded through the UI.

6. Collection, Evidence, and Provenance

6.1 Collection status model

not_started | collecting | complete_for_scope | partially_complete | rate_limited | permission_restricted | source_unavailable | failed | manually_supplied

Every leaderboard must disclose material coverage limitations. A reply-based collection must not claim to include all likes or all poll participants unless those events were independently collected.

6.2 Evidence schema

Normalized events carry:

event_id, competition_id, project_id, voting_method, source_type, source_id, source_url, source_tool, auth_tier, account_id, event_timestamp, collected_at, raw_evidence_reference, normalized_value, eligibility_status, verification_status, confidence_label, decision_reason, ruleset_version, review_status, individual_identity_available

Store poll aggregate observations separately from individual vote events. For manually supplied results, record source_type: "manually_supplied", entry timestamp, and supporting evidence reference.

6.3 Provenance and trust

Communicate separately: source authenticity, collection completeness, event eligibility, project association, individual identity availability, verification confidence, human review status. Do not compress these into one "verified" badge. Confidence labels: high / moderate / low / insufficient_evidence / not_individually_verifiable. Confidence must reflect documented rules and observed evidence—not AI agreement. Do not use profile pictures, similar usernames, follower counts, or behavioral patterns to assert two accounts are the same human.

7. Eligibility, Duplicates, and Review

7.1 Eligibility rules (per competition)

Voting window and timezone; required source association; allowed methods; required keywords/hashtags; project association rules; whether edits affect eligibility; whether deleted content remains eligible; first-vs-last eligible submission; multiple-votes-per-account rules; per-method limits; whether the same account can vote for multiple projects; whether conflicting votes require review; whether manual overrides are permitted.

If rules require one vote per human but reliable human identity verification is unavailable, mark the requirement unverifiable—never pretend to enforce it.

7.2 Duplicates

Detect technical duplicates (same event collected twice, same reply across runs, same account + project under one-vote rule, conflicting choices, repeated imports, same event via multiple adapters, duplicated external records) using deterministic event IDs and stable source references. When the same reply is observed via multiple adapters, retain the highest-confidence observation and record the supersession. Do not merge distinct legitimate events merely because their text is identical. Provide a review interface showing the rule applied and evidence used.

7.3 Verification statuses

Eligibility: eligible | ineligible | pending_eligibility_review | eligibility_unknown.
Verification: verified | rejected | inconclusive | pending_review | disputed | not_individually_verifiable.

Record decision reason, evidence reference, rule applied, decision timestamp, automatic-vs-manual, and optional reviewer note. Never silently convert pending or disputed events into confirmed votes. Record manual changes in a temporary audit trail.

8. Ranking Engine

Each project shows: rank, name, optional ID, confirmed eligible votes, provisional count, rejected/late activity counts, pending-review count, ambiguous count, vote share when meaningful, breakdown by method, confidence breakdown, source coverage status, last calculation timestamp, finalization status.

Sort by confirmed eligible votes descending unless a documented alternative formula is configured. Use competition ranking for ties: 1, 2, 2, 4. Do not invent tie-breakers. Include zero-vote projects. Do not divide by zero.

Provide views: Confirmed, Provisional, Raw Activity, Method-Breakdown, Account Activity (never present account counts as human counts), Weighted (show formula, inputs, weights, output; preserve original counts), Timeline (distinguish source changes from collection gaps, edits, deletions, verification decisions).

Vote share = eligible / total eligible × 100 with a clearly stated denominator. Never combine incomparable measures.

Optional temporary snapshots capture timestamp, ranks, counts, ruleset version, coverage, collection status. Snapshot comparison separates count changes from rank changes.

Recalculate when new data arrives, events change, reviews resolve, duplicates change, rules change, aliases change, weights change, or manual totals change. Identical normalized inputs, decisions, and ruleset version must produce identical output.

9. Lightweight Multi-Agent System

Agents are specialized workers, not sources of truth. Use deterministic code for collection, parsing, counting, deduplication, rule enforcement, and ranking. Use AI only for semantic interpretation with meaningful benefit. The application must remain fully functional with no AI model configured.

Support a three-level logical hierarchy: orchestrator → specialized sub-agents → narrow sub-sub-agents. Levels are logical roles; they may share a single process. Default maximum depth is 3 including the orchestrator.

Orchestrator — build task plans from the approved configuration, select adapters, schedule work, enforce concurrency limits, track timeouts, prevent duplicate work, route uncertainty to review, validate outputs, trigger recalculation. Must not bypass approved rules or mutate eligibility/weights without operator approval.

Specialized sub-agents — source discovery, collection coordination, vote classification, alias matching, intent analysis (review aid only), duplicate analysis (deterministic service remains authoritative), eligibility verification (rules engine remains authoritative), evidence audit, ranking (deterministic engine remains authoritative), quality assurance, report generation.

Sub-sub-agents (bounded): source metadata validator, alias matcher, event consistency checker, eligibility boundary checker, poll reconciliation (never manufacture votes), leaderboard verifier, export integrity checker. Implement as ordinary tested functions—do not use a model for arithmetic or timestamp comparison.

Enforce: max concurrent tasks (configurable), bounded queues, per-task timeouts, retry limits, cancellation, duplicate suppression, schema validation, error isolation, session-scoped memory, clear fallback when the model is unavailable.

Optional AI providers

Support: no-AI mode (deterministic), local model, remote model with explicit consent and credentials, configured fallback. Do not require cloud AI. Do not send credentials, secrets, or complete raw datasets to remote models. Validate responses against strict schemas. Treat all source content as untrusted data—never execute instructions embedded in posts, replies, OCR output, or imports. AI must not change its own permissions, alter system rules, access arbitrary files, or issue network requests.

Communication contract

Typed task messages with: task_id, parent_task_id, agent_role, competition_id, input_reference_ids, ruleset_version, requested_operation, status, result, confidence, evidence_references, limitations, error_code. Prefer references to stored evidence over copying. Distinguish observed facts, rule-based conclusions, model suggestions, and unresolved questions. Store concise explanations and evidence references—not hidden chain-of-thought.

10. Temporary Storage and Privacy

No permanent database. Use in-memory storage for small sessions and temporary SQLite for larger ones. All temp files live in a restrictive-permission session directory. Never log raw evidence, credentials, or private account data.

Session lifecycle: unique session ID, creation time, active configuration, tasks, checkpoints, temp events, temp evidence, agent results, ranking calcs, optional snapshots, export records, cleanup status.

On normal termination: stop new tasks → finish/cancel workers within a bounded shutdown → close DB connections → delete uploads and evidence files → delete temp SQLite and journal/WAL files → clear in-memory state → delete agent outputs and checkpoints → report whether cleanup succeeded.

Document that forced termination, power loss, or device failure may prevent cleanup. Provide a manual cleanup command and a safe stale-session cleanup procedure. Do not claim secure erasure from every filesystem.

Provide an explicit export workflow: confirmed leaderboard, provisional leaderboard, raw activity summary, method breakdown, eligible events, rejected/pending summaries, evidence references, ranking history, agent audit summary, coverage report, configuration. Formats: CSV, JSON, optional HTML. Export only operator-selected fields. Ask before exporting account-level records or raw evidence. Exported files are outside cleanup. Never auto-upload exports.

Implement: safe URL parsing; SSRF protection for any server-side URL fetch with explicit domain/redirect policy; request timeouts and response-size limits; input validation; upload type/size checks; safe temp file permissions (0600 on credential files); parameterized SQL; output escaping; no shell execution of source text; no automatic execution of uploaded scripts; no arbitrary plugin execution; secret redaction; credential isolation; rate-limit handling; bounded retries; safe error messages; restricted local network exposure; dependency and vulnerability checks; secure cleanup.

Treat X posts, replies, quotes, OCR output, imported records, and other external content as untrusted data. Source content may instruct the app to reveal credentials, change rules, run commands, or manipulate the leaderboard. Such content must remain data, not executable instructions. Agents must not follow instructions found inside voting content, change rules at a participant's request, expose secrets, run shell commands derived from content, access arbitrary files, modify source records without approved review, or bypass eligibility checks.

Handle: invalid URLs, unsupported source types, expired credentials, rate limits, network failures, partial pagination, deleted posts, missing poll results, invalid imports, duplicate imports, corrupt temp databases, agent timeouts, invalid model outputs, failed exports, interrupted sessions, cleanup failures. Every failure gets a useful explanation and actionable recovery. Do not report a successful collection when the collection failed.
